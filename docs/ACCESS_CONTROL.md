# IVC · Access Control and Deployment

IVC는 공개 소개 화면과 인증이 필요한 계산기를 분리합니다. 공개 회원가입은 없습니다. 최고 관리자만 이메일을 허용하고 일회용 초대를 만들거나 권한을 회수할 수 있습니다. 지정한 이메일은 IVC 자체 계정이며 Gmail 로그인·Gmail 비밀번호와 연동하지 않습니다.

## 1. 처음 실행하기

Node.js **24 이상**이 필요합니다. 기존 Vite 서버가 실행 중이면 Ctrl+C로 종료하세요.

```sh
npm ci
npm run auth:setup
npm run dev -- --port 5173
```

`auth:setup`은 최고 관리자 이메일 `eerrtteerrt12@gmail.com`을 기본값으로 사용하고, 비밀번호를 화면에 표시하지 않는 입력창에서 두 번 받습니다. 12~128자 비밀번호를 입력합니다. 지정한 초기 비밀번호로 설정할 수 있으며, 공유 전에 Account 화면에서 전용 새 비밀번호로 변경할 수 있습니다. 같은 DB에 이미 관리자가 있으면 덮어쓰지 않습니다.

- 비밀번호 원문은 코드·문서·Git에 저장하지 않습니다. 서버 DB에는 salt를 포함한 scrypt 해시를 저장합니다.
- `.ivc-data/`와 `.env*`는 Git에서 제외합니다. 서버마다 초기 설정이 필요합니다. 개발 작업 환경에서 만든 DB는 Git push로 다른 Codespace에 전달되지 않습니다.
- `IVC_ADMIN_EMAIL` / `IVC_ADMIN_PASSWORD`를 배포 플랫폼의 서버 비밀 환경변수로 지정해 초기화할 수도 있습니다. `IVC_ADMIN_PASSWORD`는 초기화 후 제거하세요. `VITE_` 접두사가 붙은 비밀값은 사용하지 않습니다.
- `npm run dev`는 계산기를 빌드한 뒤 보호 서버를 엽니다. 소스 수정 후에는 서버를 종료하고 다시 실행합니다. 예전 Vite의 자동 HMR 대신 운영과 같은 인증 경계를 사용합니다.
- 로컬 주소는 `http://127.0.0.1:5173`입니다. Codespaces는 사용 가능한 환경변수에서 HTTPS 주소를 구성합니다. 자동 인식되지 않으면 아래 `APP_ORIGIN`을 명시해야 합니다. 주소가 다르면 Host·Origin 검증 때문에 접근이 거부됩니다.

## 2. 로그인과 허용 사용자 관리

1. 사이트의 **Log in to IVC**를 누르고 관리자 이메일과 IVC 비밀번호로 로그인합니다.
2. 계산기 상단의 **Manage Access**를 엽니다.
3. **Allowed Email**과 현재 **Admin Password**를 입력하고 **Create invitation**을 누릅니다.
4. 생성된 링크를 해당 이메일 사용자에게 안전한 개인 경로로 직접 전달합니다. 서버가 이메일을 자동 발송하지는 않습니다.
5. 사용자는 링크에서 초대한 이메일과 새 비밀번호를 입력한 뒤 로그인합니다. 초대는 48시간 동안 한 번만 사용할 수 있습니다. 이메일 일치와 링크 소유로 활성화하며, 별도의 메일함 인증 서비스는 연결하지 않았습니다. 링크를 가진 사람이 계정을 활성화할 수 있으므로 공개 게시하지 마세요.
6. 권한을 회수하려면 관리자 비밀번호를 입력하고 해당 행의 **Revoke access**를 누릅니다. 미사용 초대와 해당 사용자의 기존 세션이 즉시 서버에서 폐기됩니다.
7. 다시 허용할 때는 새 초대를 만듭니다. 이전 비밀번호로 복구하지 않습니다. 멤버의 비밀번호 분실도 회수→새 초대 순서로 처리합니다.

일반 사용자는 관리자 목록/API를 이용하거나 자기 역할을 승격할 수 없습니다. 최고 관리자는 웹 API에서 삭제·회수·재초대·승격할 수 없으며, 관리 작업에는 관리자 비밀번호를 다시 확인합니다. 최고 관리자의 비밀번호 변경은 기존 비밀번호를 확인한 뒤 Account의 **Change Password**에서 진행합니다. 비밀번호 변경 시 모든 기기의 세션을 폐기합니다. 비밀번호 분실 시 공개 복구 API는 없으므로 서버 운영자가 보호된 DB 백업·비밀값 복구 절차를 별도로 관리해야 합니다.

## 3. 운영 서버 설정

정적 호스팅에 `dist/`만 올리는 방식은 인증을 적용하지 못합니다. **server/ + dist/ + Node 24 + 영구 DB 디렉터리**를 함께 운영하세요. 소스 저장소가 공개되어 있으면 소스 자체를 비밀로 만들 수 없습니다.

```sh
npm ci
npm run build
# 아래 값은 배포 플랫폼의 서버 환경 설정에 등록합니다.
export NODE_ENV=production
export APP_ORIGIN=https://ivc.example.com
export IVC_DATA_DIR=/var/lib/ivc
export HOST=127.0.0.1
export PORT=5173
npm run auth:setup
npm start
```

- `APP_ORIGIN`은 실제 접속하는 단일 HTTPS 원점입니다. 경로·쿼리·사용자 정보를 붙이지 않습니다. 운영 모드에서 누락되거나 HTTP이면 실행을 거부합니다.
- `IVC_DATA_DIR`은 이 서비스 전용 영구 저장소여야 합니다. SQLite DB 디렉터리는 0700, DB 파일은 0600으로 설정합니다. 임시 파일시스템에 배포하면 재시작 때 계정이 유실될 수 있습니다. 한 서버 인스턴스의 전용 로컬 볼륨을 기준으로 구현했습니다. 서버 중지 후 DB를 별도 비공개 백업하고 복원 시 오래된 세션을 폐기하세요.
- HTTPS는 플랫폼 또는 reverse proxy에서 종료하고, Node 포트는 프록시에서만 접근하도록 제한합니다. 프록시는 원래 Host를 보존해야 합니다. 프록시가 고정 내부 Host로 바꾸는 경우에만 운영자가 정확한 `IVC_PROXY_HOST`를 추가합니다. Codespaces에서는 플랫폼 환경변수가 있는 경우에만 현재 포트의 localhost/127.0.0.1/::1 내부 Host를 자동 허용하며, 실제 연결 상대도 loopback이어야 합니다. 공개 HTTPS 원점의 Origin 검증과 Secure 쿠키는 유지합니다. 임의의 Forwarded 헤더로 Host·프로토콜을 신뢰하지 않습니다.
- 기본 로그인 제한은 실제 연결 IP를 사용합니다. 임의 `X-Forwarded-For`를 신뢰하지 않으므로 같은 프록시/NAT 아래의 사용자는 IP별 제한을 공유할 수 있습니다. 트래픽이 많으면 신뢰 경계를 검토한 프록시의 rate limit과 중앙 계정 저장소로 확장해야 합니다.
- 원본 서버·다른 포트·기존 Vite 서버·미리보기 주소·CDN/정적 저장소가 보호되지 않은 계산기 사본을 제공하지 않도록 닫습니다. `/assets/*`나 `/solver.wasm`만 CDN에서 공개 제공하는 구성도 사용하지 않습니다.
- Codespaces에서 외부 사람에게 공유하려면 포트의 플랫폼 접근 권한도 열려 있어야 합니다. 포트를 Public으로 바꾸는 경우 반드시 이 보호 서버만 해당 포트에 연결하세요. Codespace가 중지되면 접속할 수 없으므로 지속 공유에는 별도 운영 서버를 권장합니다.

Node 서버는 `/`, `/index.html`, `/welcome.css`, `/welcome.js`, `/response.js`만 공개합니다. 계산기 문서 `/calculator`, JavaScript·Worker `/assets/*`, WASM `/solver.wasm`과 관리자 API는 서버에서 매번 세션과 권한을 확인합니다. 그 외 소스·설정·DB 파일을 제공하는 경로는 없습니다.

## 4. 보안 경계와 실제 동작

- 비밀번호: 개별 192-bit salt, scrypt N=65536/r=8/p=1, timing-safe 비교. 동시 해시 작업 수와 대기열을 제한합니다.
- 세션: 256-bit 불투명 토큰. 서버에는 토큰의 SHA-256 해시만 저장합니다. HTTPS에서는 `__Host-` / Secure / HttpOnly / SameSite=Strict / Path=/ 쿠키를 사용합니다. 8시간 절대 수명, 활동 후 30분 유휴 만료를 적용합니다. 단순 상태 폴링은 유휴 시간을 연장하지 않습니다.
- 요청 보호: 상태 변경 POST에 정확한 Origin·JSON 형식을 요구하고 로그인 이후 CSRF 토큰을 추가 검증합니다. 관리자 작업은 현재 비밀번호를 다시 확인합니다.
- 로그인 제한: IP 30회/15분, 계정 12회/15분, 전역 120회/15분. 일반·관리자·초대 단계에 별도 제한을 둡니다. 실패 이유로 계정 존재를 노출하지 않습니다.
- 출력·파일: CSP, frame 차단, MIME sniff 차단, no-referrer, HTTPS HSTS와 no-store를 적용합니다. 숫자 계산용 WebAssembly만 CSP에서 허용하며 JavaScript eval은 허용하지 않습니다. 서버는 허용한 파일 경로만 제공하고 symlink로 루트 밖을 읽지 않습니다. 비밀번호·초대 링크·세션을 요청 로그에 기록하지 않습니다.
- 계정별 작업 저장: 브라우저 프로젝트 저장 키를 사용자 ID별로 분리합니다. 기존 비로그인 프로젝트는 최고 관리자에게만 이관합니다. 다른 계정의 UI에 자동으로 섞여 표시되지 않지만 로컬 프로젝트는 암호화 금고가 아닙니다. 공용 PC에서는 JSON으로 백업하고 브라우저 데이터를 관리하세요.
- 권한 회수: 다음 서버 요청부터 즉시 차단합니다. 열려 있는 계산기 화면은 20초 간격과 창 복귀 시 재검증하고 차단합니다. 이미 전송받은 JavaScript나 내보낸 파일을 원격으로 회수하거나, 브라우저를 변조해 그 코드로 오프라인 계산하는 것까지 막지는 못합니다.

절대적인 우회 불가능을 보장하는 구현은 없습니다. 탈취한 계정/기기, 서버 관리자 권한, 공개 소스의 복제, 이미 다운로드한 계산 코드까지 제어할 수는 없습니다. 현재는 비밀번호 기반 인증이며 MFA·외부 메일함 인증·외부 침투 테스트·분산 DoS 방어는 포함하지 않습니다. 운영 TLS·백업·업데이트·접근 제어도 유지해야 합니다.

## 5. 검증

`npm test`는 기존 수학 엔진 검증에 더해 `node --test`의 실제 HTTP 보안 검증을 실행합니다. 테스트용 가짜 계정은 `tests/`에만 있고 운영 초기화 경로와 분리합니다. 보안 검증은 익명 계산기/JS/WASM 접근, 위조 쿠키/역할/Forwarded 헤더, Origin·CSRF, 권한 상승, 초대 이메일·만료·재사용, 권한 회수, 세션 만료·로그아웃·비밀번호 변경, Host·경로·요청 크기, SQL 입력·DB 파일 권한, Secure 쿠키를 포함합니다.

브라우저 검증은 테스트 전용 DB의 실제 서버에 로그인해서 수행합니다. 테스트 계정이나 인증 생략 플래그를 운영 서버에서 활성화하는 경로는 없습니다. `npm run test:e2e` 실행 전 `npm run build`를 완료하세요.

검증 결과: 기존 계산 검사 764개와 계정별 저장 분리 검사 2개, HTTP 보안 검사 27개, 로그인/초대/회수 및 기존 계산기 브라우저 시나리오 22개를 통과했습니다. TypeScript·프로덕션 빌드·핵심 코드 문서 동기화도 확인했습니다. 이는 해당 재현 시나리오의 통과이며 독립적인 침투 테스트나 모든 공격에 대한 증명은 아닙니다.

Codespaces 접속 시 `접속 주소를 확인하세요`가 표시되던 문제를 내부 Host 재작성 조건으로 재현해 수정했습니다. HTTPS 원점의 로그인→세션→보호 파일 흐름과 익명 파일 차단, 원격 연결·다른 포트·위조 Forwarded 헤더·잘못된 Origin의 차단을 추가 검증했습니다. 이미 초기화한 관리자 DB는 그대로 사용하므로 재설정하지 않습니다.

로그인 중 `Unexpected end of JSON input`은 비어 있는 HTTP 응답을 JSON으로 해석하던 표시 오류였습니다. API 응답에 UTF-8 Content-Length와 IVC 응답 표시를 추가하고, 빈 본문·HTML·중계 오류를 성공으로 처리하지 않도록 수정했습니다. 실제 실패 상태(401/403/404/429/502 등)를 표시하며, 로그인 POST가 리디렉션을 따라 자격 증명을 다른 주소로 전송하지 않도록 차단합니다. 404의 실제 발생 지점은 실패 요청의 Request URL·Method·응답 표시와 실행 중인 서버 버전을 확인해야 하며, 화면 오류 메시지만으로 비밀번호 불일치나 특정 프록시 원인이라고 단정하지 않습니다.

## 로그인 POST 404의 분리 진단

브라우저 요청이 현재 사이트의 `POST /api/login`임에도 빈 404를 받는 환경을 위해 클라이언트 인증 요청을 `/ivc-auth/*`로 분리했습니다. 기존 `/api/*`는 같은 서버 핸들러의 호환 경로로 유지하며, 새 경로도 세션·Origin·CSRF·관리자 권한 검사를 그대로 통과해야 합니다. 프록시가 `/api/*`를 빈 404로 차단하는 조건을 브라우저에서 재현해 로그인과 계산기 진입·로그아웃을 확인합니다. 이는 사용자 Codespace에서 중계가 원인임을 직접 증명한 것은 아닙니다.

업데이트 후 기존 포트의 서버를 종료하고 `npm run dev -- --port 5173`으로 시작합니다. 터미널에 `Authentication routes: /ivc-auth (auth-v2)`가 있어야 새 버전입니다. `EADDRINUSE`이면 기존 서버가 아직 포트를 사용 중이며 새 서버가 시작되지 않은 것입니다. 계정 DB를 다시 초기화할 필요는 없습니다.

- 사이트 주소 뒤 `/ivc-auth/status`를 열면 로그인 없이 `{service:"IVC",api:"/ivc-auth",version:"auth-v2"}` 형태의 공개 상태 응답을 반환합니다. 계정·세션·비밀값은 포함하지 않습니다.
- 인증 POST가 IVC 서버에 도착하면 고정된 작업명과 HTTP 상태만 터미널에 기록합니다. 예: `IVC auth login: HTTP 200`. 이메일·비밀번호·Cookie·초대 링크·요청 본문은 기록하지 않습니다.
- 브라우저에서 로그인했는데 해당 로그가 없으면 실행 중인 서버나 중계 경로를 먼저 확인합니다. 로그가 401이면 계정 자격 증명을, 403이면 Origin/CSRF/권한 검사를, 429이면 시도 제한을 확인합니다.

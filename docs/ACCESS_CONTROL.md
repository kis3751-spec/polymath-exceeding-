# IVC · Access Control and Deployment

IVC는 공개 소개 화면과 인증이 필요한 계산기를 분리합니다. 공개 회원가입은 없습니다. 최고 관리자만 이메일을 허용하고 일회용 초대를 만들거나 권한을 회수할 수 있습니다. 지정한 이메일은 IVC 자체 계정이며 Gmail 로그인·Gmail 비밀번호와 연동하지 않습니다.

## 1. 처음 실행하기

Node.js **24 이상**이 필요합니다. 기존 Vite 서버가 실행 중이면 Ctrl+C로 종료하세요.

```sh
npm ci
npm run auth:setup
npm run dev
```

`auth:setup`은 최고 관리자 이메일 `eerrtteerrt12@gmail.com`을 기본값으로 사용하고, 비밀번호를 화면에 표시하지 않는 입력창에서 두 번 받습니다. 12~128자 비밀번호를 입력합니다. 지정한 초기 비밀번호로 설정할 수 있으며, 공유 전에 Account 화면에서 전용 새 비밀번호로 변경할 수 있습니다. 같은 DB에 이미 관리자가 있으면 덮어쓰지 않습니다.

- 비밀번호 원문은 코드·문서·Git에 저장하지 않습니다. 서버 DB에는 salt를 포함한 scrypt 해시를 저장합니다.
- `.ivc-data/`와 `.env*`는 Git에서 제외합니다. 서버마다 초기 설정이 필요합니다. 개발 작업 환경에서 만든 DB는 Git push로 다른 Codespace에 전달되지 않습니다.
- `IVC_ADMIN_EMAIL` / `IVC_ADMIN_PASSWORD`를 배포 플랫폼의 서버 비밀 환경변수로 지정해 초기화할 수도 있습니다. `IVC_ADMIN_PASSWORD`는 초기화 후 제거하세요. `VITE_` 접두사가 붙은 비밀값은 사용하지 않습니다.
- `npm run dev`는 계산기를 빌드한 뒤 보호 서버를 엽니다. 소스 수정 후에는 서버를 종료하고 다시 실행합니다. 예전 Vite의 자동 HMR 대신 운영과 같은 인증 경계를 사용합니다.
- 로컬 주소는 `http://127.0.0.1:5173`입니다. Codespaces 기본 포트는 **5180**이며 사용 가능한 환경변수에서 HTTPS 주소를 구성합니다. 일반 로컬 기본 포트는 5173입니다. 실행·공유·진단은 같은 기본값을 사용하며 명시한 PORT와 --port는 우선합니다. 자동 인식되지 않으면 아래 `APP_ORIGIN`을 명시해야 합니다. 주소가 다르면 Host·Origin 검증 때문에 접근이 거부됩니다.

## 2. 다른 사람 초대하기

### Codespaces의 GitHub 로그인과 IVC 로그인

**상대방에게 GitHub 개인 계정이 있어도 개인 Codespace의 Private 포트 사용 권한이 생기지는 않습니다.** GitHub 로그인 후 404가 보이면 IVC에 도달하기 전 플랫폼 접근 제어에서 막혔을 수 있습니다. IVC의 허용 이메일 등록으로 GitHub 포트 권한을 바꿀 수는 없습니다. 임의의 다른 사람을 IVC 계정으로 초대할 때는 포트의 소개·로그인 화면에 GitHub 로그인 없이 도달하도록 설정해야 합니다.

서버를 실행한 터미널은 그대로 두고, **새 터미널**에서 실행합니다.

```sh
npm run share:codespaces
```

이 명령은 현재 포트의 최신 보호 서버와 익명 `/solver.wasm` 요청의 401 차단을 먼저 확인합니다. 그 뒤 `gh codespace ports visibility`로 해당 포트만 Public으로 설정하고, 로그인 쿠키 없이 공유 주소가 같은 IVC 인스턴스로 연결되는지 확인합니다. 서버 확인에 실패하면 포트 공개를 시도하지 않습니다. `PORT`를 변경했다면 같은 값을 지정하세요. GitHub CLI 권한이 없으면 **Ports → 5180 우클릭 → Port Visibility → Public**으로 직접 바꿉니다. 조직 정책으로 Public이 금지되어 있다면 별도의 HTTPS 호스팅이 필요합니다. 서버 시작만으로 포트를 자동 공개하지는 않습니다.

Public은 IVC의 로그인 화면에 도착하게 하는 설정입니다. 계산기 문서·Worker·WASM과 관리자 API의 인증은 유지됩니다. GitHub OAuth를 IVC 로그인으로 사용하지 않습니다.

### 관리자 화면과 초대 수락

1. 관리자 본인의 IVC 이메일·비밀번호로 로그인한 뒤 **Manage Access**를 엽니다.
2. **Sharing → Check connection**은 참고 연결 진단입니다. Server check passed는 서버 네트워크에서 소개·로그인 파일을 확인한 상태, API connected는 상태 API가 현재 IVC와 일치하지만 일부 파일 검사가 미완료인 상태입니다. 파일 검사가 실패하거나 연결 검사를 실행하지 않아도 최고 관리자는 초대를 발급·재설정할 수 있습니다. 실제 상대방의 브라우저 접속은 별도로 확인합니다.
3. **Allowed Email**에는 상대방 이메일, **Admin Password**에는 **현재 로그인한 관리자 본인의 IVC 비밀번호**를 입력합니다. 상대방의 비밀번호나 Gmail/GitHub 비밀번호를 입력하는 곳이 아닙니다.
4. **Create invitation**을 누르고 생성한 링크·코드를 해당 사용자에게 안전한 개인 경로로 직접 전달합니다. 이메일은 자동 발송되지 않습니다. 초대는 48시간 동안 한 번만 사용할 수 있습니다.
5. 사용자가 링크를 열면 초대된 이메일이 읽기 전용으로 표시됩니다. 본인의 새 IVC 비밀번호를 정하고 **Activate account**를 누르면 바로 계산기로 이동합니다. 메일함 소유 인증 서비스는 연결하지 않았습니다. 링크·코드를 가진 사람이 해당 계정을 활성화할 수 있으므로 초대 대상에게만 전달합니다.
6. 링크에서 초대 화면을 잃었으면 사이트의 **Log in → Have an invitation code?**에서 전달받은 43자 코드를 입력합니다. GitHub 로그인 과정에서 URL fragment가 사라져도 이 경로로 복구할 수 있습니다. 원래 링크·코드 자체가 만료·사용·회수되었다면 새 초대를 받아야 합니다.
7. 초대 검증에 성공한 뒤에만 URL에서 비밀값을 지웁니다. 서버 DB에는 15분짜리 설정 흐름의 해시를 저장하고 HttpOnly 쿠키로 이어갑니다. 설정 화면을 새로고침해도 이메일과 흐름을 복원합니다. 15분이 지나면 원래 링크·코드로 다시 열 수 있습니다. 비밀번호와 초대 토큰을 localStorage/sessionStorage에 보관하지 않습니다.

### 재발급·회수·비밀번호 분실

목록은 Active / Invited / Invitation expired / Revoked를 구분합니다. 미활성·만료·회수 계정의 **Reissue invitation**은 이전 링크와 설정 흐름을 폐기하고 새 초대를 만듭니다. 활성 계정의 **Reset account**는 관리자 비밀번호와 확인 대화상자를 거쳐 기존 비밀번호·모든 세션을 폐기하고 재설정 초대를 발급합니다. 기존 비밀번호로 로그인하거나 폐기한 초대로 계정을 살릴 수 없습니다.

**Revoke access**는 접근 권한·모든 세션·미사용 초대·설정 흐름을 서버에서 즉시 폐기합니다. 다시 허용할 때는 새 초대가 필요합니다. 초대 수락은 트랜잭션에서 최종 상태를 재검사하므로 두 브라우저가 동시에 수락해도 한 번만 성공합니다.

일반 사용자는 관리자 목록/API를 이용하거나 자기 역할을 승격할 수 없습니다. 최고 관리자 계정은 재설정·회수·재초대할 수 없습니다. 자신의 **Change Password**는 기존 비밀번호를 확인하고 모든 기기 세션을 폐기합니다. 최고 관리자 비밀번호 분실에는 공개 복구 API가 없으므로 운영자가 보호된 DB 백업·비밀값 복구 절차를 별도로 관리해야 합니다.

## 3. 운영 서버 설정

정적 호스팅에 `dist/`만 올리는 방식은 인증을 적용하지 못합니다. **server/ + dist/ + Node 24 + 영구 DB 디렉터리**를 함께 운영하세요. 소스 저장소가 공개되어 있으면 소스 자체를 비밀로 만들 수 없습니다.

```sh
npm ci
npm run build
# 아래 값은 배포 플랫폼의 서버 환경 설정에 등록합니다.
export NODE_ENV=production
export APP_ORIGIN=https://ivc.example.com
export IVC_DATA_DIR=/var/lib/ivc
export HOST=127.0.0.1
export PORT=5173
npm run auth:setup
npm start
```

- `APP_ORIGIN`은 실제 접속하는 단일 HTTPS 원점입니다. 경로·쿼리·사용자 정보를 붙이지 않습니다. 운영 모드에서 누락되거나 HTTP이면 실행을 거부합니다.
- `IVC_DATA_DIR`은 이 서비스 전용 영구 저장소여야 합니다. SQLite DB 디렉터리는 0700, DB 파일은 0600으로 설정합니다. 임시 파일시스템에 배포하면 재시작 때 계정이 유실될 수 있습니다. 한 서버 인스턴스의 전용 로컬 볼륨을 기준으로 구현했습니다. 서버 중지 후 DB를 별도 비공개 백업하고 복원 시 오래된 세션을 폐기하세요.
- HTTPS는 플랫폼 또는 reverse proxy에서 종료하고, Node 포트는 프록시에서만 접근하도록 제한합니다. 프록시는 원래 Host를 보존해야 합니다. 프록시가 고정 내부 Host로 바꾸는 경우에만 운영자가 정확한 `IVC_PROXY_HOST`를 추가합니다. Codespaces에서는 플랫폼 환경변수가 있는 경우에만 현재 포트의 localhost/127.0.0.1/::1 내부 Host를 자동 허용하며, 실제 연결 상대도 loopback이어야 합니다. 공개 HTTPS 원점의 Origin 검증과 Secure 쿠키는 유지합니다. 임의의 Forwarded 헤더로 Host·프로토콜을 신뢰하지 않습니다.
- 기본 로그인 제한은 실제 연결 IP를 사용합니다. 임의 `X-Forwarded-For`를 신뢰하지 않으므로 같은 프록시/NAT 아래의 사용자는 IP별 제한을 공유할 수 있습니다. 트래픽이 많으면 신뢰 경계를 검토한 프록시의 rate limit과 중앙 계정 저장소로 확장해야 합니다.
- 원본 서버·다른 포트·기존 Vite 서버·미리보기 주소·CDN/정적 저장소가 보호되지 않은 계산기 사본을 제공하지 않도록 닫습니다. `/assets/*`나 `/solver.wasm`만 CDN에서 공개 제공하는 구성도 사용하지 않습니다.
- Codespaces에서 외부 사람에게 공유하려면 포트의 플랫폼 접근 권한도 열려 있어야 합니다. 포트를 Public으로 바꾸는 경우 반드시 이 보호 서버만 해당 포트에 연결하세요. Codespace가 중지되면 접속할 수 없으므로 지속 공유에는 별도 운영 서버를 권장합니다.

Node 서버는 `/`, `/index.html`, `/welcome.css`, `/welcome.js`, `/response.js`, `/auth-client.js`만 공개합니다. 계산기 문서 `/calculator`, JavaScript·Worker `/assets/*`, WASM `/solver.wasm`과 관리자 API는 서버에서 매번 세션과 권한을 확인합니다. 그 외 소스·설정·DB 파일을 제공하는 경로는 없습니다.

## 4. 보안 경계와 실제 동작

- 비밀번호: 개별 192-bit salt, scrypt N=65536/r=8/p=1, timing-safe 비교. 동시 해시 작업 수와 대기열을 제한합니다.
- 세션: 256-bit 불투명 토큰. 서버에는 토큰의 SHA-256 해시만 저장합니다. HTTPS에서는 `__Host-` / Secure / HttpOnly / SameSite=Strict / Path=/ 쿠키를 사용합니다. 30일 절대 수명, 마지막 실제 활동 후 7일 유휴 만료를 적용합니다. 단순 상태 폴링은 유휴 시간을 연장하지 않습니다.
- 요청 보호: 상태 변경 POST에 정확한 Origin·JSON 형식을 요구하고 로그인 이후 CSRF 토큰을 추가 검증합니다. 관리자 작업은 현재 비밀번호를 다시 확인합니다.
- 로그인 제한: IP 30회/15분, 계정 12회/15분, 전역 120회/15분. 일반·관리자·초대 단계에 별도 제한을 둡니다. 실패 이유로 계정 존재를 노출하지 않습니다.
- 출력·파일: CSP, frame 차단, MIME sniff 차단, no-referrer, HTTPS HSTS와 no-store를 적용합니다. 숫자 계산용 WebAssembly만 CSP에서 허용하며 JavaScript eval은 허용하지 않습니다. 서버는 허용한 파일 경로만 제공하고 symlink로 루트 밖을 읽지 않습니다. 비밀번호·초대 링크·세션을 요청 로그에 기록하지 않습니다.
- 계정별 작업 저장: 브라우저 프로젝트 저장 키를 사용자 ID별로 분리합니다. 기존 비로그인 프로젝트는 최고 관리자에게만 이관합니다. 다른 계정의 UI에 자동으로 섞여 표시되지 않지만 로컬 프로젝트는 암호화 금고가 아닙니다. 공용 PC에서는 JSON으로 백업하고 브라우저 데이터를 관리하세요.
- 권한 회수: 다음 서버 요청부터 즉시 차단합니다. 열려 있는 계산기 화면은 20초 간격과 창 복귀 시 재검증하고 차단합니다. 이미 전송받은 JavaScript나 내보낸 파일을 원격으로 회수하거나, 브라우저를 변조해 그 코드로 오프라인 계산하는 것까지 막지는 못합니다.

절대적인 우회 불가능을 보장하는 구현은 없습니다. 탈취한 계정/기기, 서버 관리자 권한, 공개 소스의 복제, 이미 다운로드한 계산 코드까지 제어할 수는 없습니다. 현재는 비밀번호 기반 인증이며 MFA·외부 메일함 인증·외부 침투 테스트·분산 DoS 방어는 포함하지 않습니다. 운영 TLS·백업·업데이트·접근 제어도 유지해야 합니다.

## 5. 검증

`npm test`는 기존 수학 엔진 검증에 더해 `node --test`의 실제 HTTP 보안 검증을 실행합니다. 테스트용 가짜 계정은 `tests/`에만 있고 운영 초기화 경로와 분리합니다. 보안 검증은 익명 계산기/JS/WASM 접근, 위조 쿠키/역할/Forwarded 헤더, Origin·CSRF, 권한 상승, 초대 이메일·만료·재사용, 권한 회수, 세션 만료·로그아웃·비밀번호 변경, Host·경로·요청 크기, SQL 입력·DB 파일 권한, Secure 쿠키를 포함합니다.

브라우저 검증은 테스트 전용 DB의 실제 서버에 로그인해서 수행합니다. 테스트 계정이나 인증 생략 플래그를 운영 서버에서 활성화하는 경로는 없습니다. `npm run test:e2e` 실행 전 `npm run build`를 완료하세요.

검증 결과: 기존 계산 검사 764개와 계정별 저장 분리 검사 2개, HTTP 보안 검사 27개, 로그인/초대/회수 및 기존 계산기 브라우저 시나리오 22개를 통과했습니다. TypeScript·프로덕션 빌드·핵심 코드 문서 동기화도 확인했습니다. 이는 해당 재현 시나리오의 통과이며 독립적인 침투 테스트나 모든 공격에 대한 증명은 아닙니다.

Codespaces 접속 시 `접속 주소를 확인하세요`가 표시되던 문제를 내부 Host 재작성 조건으로 재현해 수정했습니다. HTTPS 원점의 로그인→세션→보호 파일 흐름과 익명 파일 차단, 원격 연결·다른 포트·위조 Forwarded 헤더·잘못된 Origin의 차단을 추가 검증했습니다. 이미 초기화한 관리자 DB는 그대로 사용하므로 재설정하지 않습니다.

로그인 중 `Unexpected end of JSON input`은 비어 있는 HTTP 응답을 JSON으로 해석하던 표시 오류였습니다. API 응답에 UTF-8 Content-Length와 IVC 응답 표시를 추가하고, 빈 본문·HTML·중계 오류를 성공으로 처리하지 않도록 수정했습니다. 실제 실패 상태(401/403/404/429/502 등)를 표시하며, 로그인 POST가 리디렉션을 따라 자격 증명을 다른 주소로 전송하지 않도록 차단합니다. 404의 실제 발생 지점은 실패 요청의 Request URL·Method·응답 표시와 실행 중인 서버 버전을 확인해야 하며, 화면 오류 메시지만으로 비밀번호 불일치나 특정 프록시 원인이라고 단정하지 않습니다.

## 로그인 POST 404의 분리 진단

브라우저 요청이 현재 사이트의 `POST /api/login`임에도 빈 404를 받는 환경을 위해 클라이언트 인증 요청을 `/ivc-auth/*`로 분리했습니다. 기존 `/api/*`는 같은 서버 핸들러의 호환 경로로 유지하며, 새 경로도 세션·Origin·CSRF·관리자 권한 검사를 그대로 통과해야 합니다. 프록시가 `/api/*`를 빈 404로 차단하는 조건을 브라우저에서 재현해 로그인과 계산기 진입·로그아웃을 확인합니다. 이는 사용자 Codespace에서 중계가 원인임을 직접 증명한 것은 아닙니다.

업데이트 후 기존 포트의 서버를 종료하고 `npm run dev`으로 시작합니다. 터미널에 `Authentication routes: /ivc-auth (auth-v4)`가 있어야 새 버전입니다. `EADDRINUSE`이면 기존 서버가 아직 포트를 사용 중이며 새 서버가 시작되지 않은 것입니다. 계정 DB를 다시 초기화할 필요는 없습니다.

- 사이트 주소 뒤 `/ivc-auth/status`를 열면 로그인 없이 `{service:"IVC",api:"/ivc-auth",version:"auth-v4",accessControl:"invite-only",instance:"…"}` 형태의 공개 상태 응답을 반환합니다. 계정·세션·초대 비밀값은 포함하지 않습니다. instance는 현재 프로세스를 구별하는 공개 난수이며 인증 토큰이 아닙니다.
- 인증 POST가 IVC 서버에 도착하면 고정된 작업명과 HTTP 상태만 터미널에 기록합니다. 예: `IVC auth login: HTTP 200`. 이메일·비밀번호·Cookie·초대 링크·요청 본문은 기록하지 않습니다.
- 브라우저에서 로그인했는데 해당 로그가 없으면 실행 중인 서버나 중계 경로를 먼저 확인합니다. 로그가 401이면 계정 자격 증명을, 403이면 Origin/CSRF/권한 검사를, 429이면 시도 제한을 확인합니다.

## Codespaces Origin 재작성 처리 (auth-v3)

서버에 `IVC auth login: HTTP 403`이 남으면 요청은 IVC까지 도착했지만 출처 검사에서 거부되었을 수 있습니다. auth-v3는 로그인/초대 제출 전 `/ivc-auth/csrf`에서 무작위 토큰을 받으며, 같은 값의 HttpOnly·SameSite=Strict 쿠키를 HTTPS에서 \_\_Host-/Secure 조건으로 발급합니다. 토큰은 메모리에만 보관하고 POST의 X-CSRF-Token으로 돌려줍니다.

공개 원점과 다른 Origin은 기본적으로 계속 거부합니다. Codespaces 환경변수가 있고 실제 연결 상대가 loopback이며 Host가 승인된 경우에만, 현재 포트의 정확한 localhost/127.0.0.1/::1 Origin으로 재작성된 요청을 검토합니다. 이 경우에도 로그인 전 토큰과 쿠키가 일치하거나 이미 로그인한 세션의 CSRF 토큰이 맞아야 합니다. Origin이 생략되면 same-origin Fetch Metadata와 토큰 증명이 모두 필요합니다. cross-site Metadata, 임의의 다른 사이트 Origin, 다른 포트, 위조/누락 토큰을 허용하지 않습니다.

성공한 로그인에는 계속 비밀번호 검증이 필요하고, 관리자 기능에는 세션 권한과 재확인을 그대로 적용합니다. 새로운 출처 진단 로그는 비밀값을 빼고 공개 원점과 상태만 표시합니다. `origin/proof mismatch` 또는 `cross-site request`의 구체적인 거부 사유를 확인할 수 있습니다.

이 보완의 HTTP 보안 검사 31개와 로그인 브라우저 검사 7개를 통과했습니다. 브라우저 검사에는 전달 중 Origin만 localhost로 바꾸는 상황에서 로그인·로그아웃하는 시나리오가 포함됩니다. 운영 Codespace에서의 성공 여부는 별도로 확인해야 하며, 재현 검사를 실제 운영 접속 성공으로 간주하지 않습니다.

## 계산 Worker의 모듈 로딩

일시적인 네트워크 실패·인증 쿠키 전달·업데이트 전 파일 참조가 있으면 Worker에서 `Failed to fetch dynamically imported module`이 날 수 있습니다. 오류가 사라졌다는 사실만으로 원인을 확정하지 않습니다. 재발 위험을 줄이기 위해 과학 계산 Worker는 ODE·회귀·적분·최적화를 정적 import하고, Vite Worker 출력은 inlineDynamicImports로 한 번들에 포함합니다. 계산 중 하위 엔진 청크를 다시 네트워크에서 가져오지 않습니다. 계산 알고리즘은 바꾸지 않았습니다.

두 계산 Worker를 credentials=include로 시작하고 WASM도 인증 쿠키를 포함해 요청합니다. 계산 파일은 계속 로그인 세션이 필요하며 공개 제공하지 않습니다. 파일 오류가 발생하면 승인된 파일명과 HTTP 상태만 `IVC asset …: HTTP …`로 기록합니다. 실행 중인 브라우저가 업데이트 전 파일을 참조하는 경우에는 모델을 저장하고 화면을 새로고침해야 할 수 있습니다.

`playwright.https.config.ts`는 로컬 임시 인증서(OpenSSL 필요)와 실제 HTTPS 서버에서 Secure/HttpOnly/\_\_Host 세션 쿠키를 검증합니다. 테스트 인증서는 임시 디렉터리에 생성·삭제하며 운영 TLS 검증을 끄지 않습니다. 모든 과학 계산 모듈의 계산·그래프와 하위 엔진 청크 추가 요청이 없는지를 확인합니다.

Worker 묶음 변경 후 기존 단위 검사 766개와 HTTPS 브라우저 시나리오 17개를 확인했습니다. 전용 로딩 검사는 ODE·세 가지 회귀·적분·두 최적화 모듈을 차례로 열고, 추가 엔진 청크 요청이 없으며 Secure 쿠키로 계산하고 익명 컨텍스트에서는 Worker/WASM 파일이 차단되는지 검사합니다. 사용자의 일시적 오류 자체는 HTTP 상태를 확보하지 못했으므로 원인을 단정하지 않습니다.

## 초대·공유 개선 검증 (auth-v4)

외부 공유 검사는 고정된 APP_ORIGIN만 사용하며 임의 URL을 받지 않습니다. 리디렉션을 따라가거나 로그인 쿠키를 보내지 않고, 시간·응답 크기를 제한하고 현재 인스턴스를 대조합니다. 관리자만 결과를 조회할 수 있고 동시 검사는 합칩니다. Check connection은 새 검사를 요청하고 진단 결과만 캐시합니다. 초대 생성·재설정은 이 진단을 호출하거나 기다리지 않습니다. 해당 작업은 출처·CSRF·최고 관리자 권한·현재 비밀번호 재확인과 세션 최종 확인을 통과해야 합니다.

이번 변경은 계산 단위 검사 **766개**, 인증·초대 HTTP 검사 **46개**, 실제 HTTPS 브라우저 시나리오 **15개**를 통과했습니다. 프로덕션 빌드와 핵심 코드 문서 동기화도 확인했습니다. 기존 DB를 열어 최고 관리자·세션·미사용 초대를 보존한 채 설정 흐름 테이블을 추가하는 경로와, 활성화 직후 재설정이 발생할 때 폐기한 세션을 다시 발급하지 않는 경로를 별도로 검사했습니다.

HTTP 회귀 검사에 설정 흐름 복원·만료·위조/중복 쿠키·다른 이메일·동시 수락·재발급·회수·재설정·최고 관리자 보호를 추가했습니다. 외부 GitHub 리디렉션·404·HTML·이전 서버 인스턴스와 공유 명령의 실패 조건도 모의 응답으로 검증합니다. 실제 HTTPS 브라우저에서는 별도 익명 컨텍스트로 링크와 코드 수락, 새로고침 후 복원, 자동 로그인, 회수·재설정 후 차단과 계산 Worker 로딩을 확인합니다. 사용자의 실제 Codespace 포트 설정은 이 작업 환경에서 바꾸거나 실제 외부 접속까지 확인한 것이 아닙니다.

Codespaces는 개발 환경입니다. Public 설정이 되어도 정지·삭제·주소 변경·조직 정책·GitHub 서비스 장애는 애플리케이션 코드만으로 해결할 수 없습니다. 계속 같은 주소를 제공하려면 위 운영 설정의 HTTPS 원점·영구 DB·자동 재시작 서비스가 있는 상시 호스팅에 배포해야 합니다. DB를 지우거나 auth:setup을 반복하는 것은 포트 문제의 해결책이 아닙니다.

## Public 설정 후 소개 화면부터 404인 경우

Public은 플랫폼 접근 권한이며 서버를 실행하거나 포트 전달의 잘못된 대상까지 고치지는 않습니다. 정상 시작 로그의 외부 HTTPS 주소는 Node 서버 자체가 TLS를 처리한다는 뜻도 아닙니다. 현재 구현은 Codespaces 내부에서 HTTP를 받고 GitHub의 HTTPS 프록시를 통과하므로 **Port Protocol=HTTP**가 맞습니다.

수신 주소는 Codespaces 환경일 때 기본 `0.0.0.0`, 일반 로컬·운영 환경일 때 `127.0.0.1`로 구분합니다. `HOST`를 명시하면 그 값이 우선합니다. 외부 HTTPS 원점 없이 HTTP를 모든 인터페이스에 여는 설정은 계속 거부합니다. 수신 인터페이스를 늘려도 허용 Host·Origin·CSRF, 로그인·계산 파일·관리자 권한 검사는 유지됩니다. 실제 컨테이너 인터페이스에 HTTP 요청을 보내 소개 화면·상태 응답은 도달하고 계산 파일·관리자 목록은 익명 차단되며 임의 Host는 거부되는지 회귀 검사합니다. 이는 포트 전달 호환성 보완이며, 사용자 화면의 404 원인을 증거 없이 이 설정 하나로 확정하는 것은 아닙니다.

Codespaces에서는 시작 후 자동으로 `IVC local check`와 `IVC public check`를 출력합니다. 시작할 때뿐 아니라 필요할 때 다음 명령을 **서버가 실행 중인 터미널과 다른 새 터미널**에서 실행할 수 있습니다.

```sh
npm run diagnose:codespaces
```

- Local=ready: 현재 로컬 포트의 IVC 상태 API·소개 HTML·익명 WASM 차단이 정상입니다. 공개 주소만 실패하면 GitHub 포트 전달·주소·Codespace 실행 상태를 확인합니다.
- Local=unavailable: 포트 연결 실패 또는 최신 IVC 상태 응답을 확인하지 못했습니다. 실행 중인 서버와 터미널 오류부터 확인합니다.
- Local=gateway-error: 상태 API는 도달했지만 소개 HTML 파일을 제공하지 못했습니다. `server/gateway/` 파일과 실행 경로를 확인합니다.
- Local=unprotected: 익명 계산 파일 차단을 확인하지 못했습니다. 공유를 계속하기 전에 보호 서버를 확인합니다.
- Public=blocked (HTTP 404): 로컬 IVC가 정상이라도 공유 주소에서 실패할 수 있습니다. Ports에서 현재 포트 전달 항목을 Stop Forwarding한 뒤 Forward a Port로 같은 포트를 다시 추가하고 HTTP·Public으로 설정합니다. Open in Browser의 주소로 다시 열어 옛 주소·북마크를 배제합니다.

진단은 공개 상태 API·소개 HTML 헤더·익명 파일 차단만 확인하며 비밀번호·세션·초대 코드를 전송하거나 출력하지 않습니다. Public 검사는 현재 프로세스와 일치하는지도 확인합니다. 현재 작업 환경은 사용자의 Codespace가 아니며 외부 Codespaces 도메인 접속도 네트워크 정책상 제한되어 있어, 사용자의 실제 공개 주소가 복구되었다고 대신 확인할 수는 없습니다.

## 5180 복구 확인과 Ready 판정 범위

## 새로고침·관리 화면·재로그인의 세션 복구

기존 유효한 세션 쿠키가 남은 상태에서 새 로그인용 토큰을 제출하면, 프록시의 Origin 재작성 경로에서 기존 세션의 다른 CSRF 토큰을 기대하여 403을 내던 조건을 재현했습니다. 로그인·초대 시작·초대 수락에서는 쿠키와 일치하는 로그인 전 토큰도 사용할 수 있게 구분합니다. 관리자 쓰기·로그아웃·비밀번호 변경은 현재 세션 CSRF를 계속 요구합니다. cross-site 요청·임의 Origin·원격 peer의 내부 Host 예외를 허용하지 않습니다. Codespaces의 정확한 현재 포트·loopback peer·자체 0.0.0.0 수신 주소 예외에도 유효한 토큰이 필요합니다.

로그인 전 토큰은 같은 브라우저 쿠키가 유효하면 재사용합니다. 두 탭이 최초 토큰을 동시에 받아 충돌해도 ENTRY_CSRF가 확인된 경우 한 번만 다시 발급받아 제출합니다. 관리자 작업은 현재 세션을 먼저 확인하고, 기존에 선택한 계정 ID와 같을 때 새 CSRF를 사용합니다. SESSION_CSRF로 쓰기 이전에 거부된 경우에만 한 번 갱신합니다. 다른 계정으로 바뀌었거나 네트워크 응답이 불명확한 쓰기는 자동 재실행하지 않습니다.

브라우저 공통 auth-client.js를 소개·관리 화면과 계산기에서 함께 사용합니다. 서버의 SESSION_REQUIRED가 있는 401만 실제 로그인 종료로 처리합니다. 일반 프록시 401·HTML·연결 실패는 쿠키 삭제나 즉시 로그아웃으로 바꾸지 않습니다. 계산기 모델을 마운트 상태로 보존하고 연결 확인 화면으로 덮은 뒤 다시 확인합니다. 확인 중 화면은 inert로 조작을 막으며, 실제 만료·회수는 서버가 계속 결정합니다. 세션 GET은 Set-Cookie를 다시 쓰지 않아 늦게 도착한 이전 응답이 새 로그인 쿠키를 덮지 않게 합니다.

세션 복구 수정 시에는 기존 만료 기준을 유지했으며, 이후 사용자의 명시적 승인으로 30일 절대 만료·7일 유휴 만료를 적용했습니다. Secure/HttpOnly/SameSite=Strict 쿠키, 최고 관리자 고정 ID, 비밀번호 재확인·권한 회수 기준은 유지합니다. 관리 화면에서도 실제 포인터·키보드 조작에 따른 활동을 보내며 수동 상태 폴링만으로 유휴 만료를 연장하지 않습니다. DB 경로가 같은 정상 서버 재시작은 기존 세션을 지우지 않습니다.

검증에는 실제 유효 쿠키와 재작성된 Origin으로 재로그인하기, 기존 쿠키의 보안 토큰 충돌, 토큰 갱신 중 계정 전환 방지, 알 수 없는 쓰기 결과를 재시도하지 않기, DB 재개방·서버 재시작 후 쿠키 복원을 포함합니다. ## Public 설정과 소개 화면 검사 구분 · 2026-11-11

## 기존 소개 주소 응답의 재사용 방지 · 2026-11-11

사용자 측에서 `/ivc-auth/status`와 로그인 JS/CSS는 현재 IVC의 200 응답을 받았지만 `/`는 IVC 표식과 로그인 폼이 없는 HTML을 반환했습니다. 새 쿼리가 붙은 동일 Origin 주소에서는 소개 화면과 실제 계산기 로그인이 정상 동작한다고 사용자가 확인했습니다. 캐시 또는 전달 경로의 기존 주소 응답 문제로 범위를 좁혔으며, 특정 중간 계층의 내부 원인까지 입증한 것은 아닙니다.

소개 화면 링크에 새 공개 `_ivc_page` 식별자를 붙입니다. 이 값은 매 탐색·공개 검사마다 새로 만들고 브라우저 저장소의 인증 수단으로 사용하지 않습니다. 관리/계정 링크, 로그아웃·비밀번호 변경·실제 만료 후 이동, 익명 계산기 리디렉션, 소개 페이지 Home 링크와 신규 초대 링크에 적용합니다. 초대 토큰은 계속 fragment에 남으며 서버 요청의 쿼리에는 넣지 않습니다. 경로는 `/`만 허용하고 다른 Origin이나 계산 파일 경로를 이 유틸리티로 만들 수 없습니다.

브라우저·공유용 `Site`는 쿼리를 포함한 전체 주소이고, 서버 설정 `Origin`은 경로·쿼리 없는 원점입니다. 공개 검사도 출력된 Site 주소를 실제로 검증합니다. IVC 내용이 아닌 HTML을 성공으로 간주하지 않고, 권한·Cookie·Origin/CSRF·관리자 비밀번호·접근 회수는 기존대로 검사합니다. 계산기 경로·포트·계정 DB·쿠키 경로·localStorage Origin은 그대로입니다.

임시 DB의 인증 회귀 73개와 HTTPS 브라우저 시나리오 18개를 통과했습니다. 기본 소개 주소만 오래된 404로 대체하는 조건에서 관리 화면, 초대 수락·새로고침·로그아웃과 비회원 계산 파일 차단을 검증했습니다. 사용자 Codespace에 새 코드가 적용되려면 Git 업데이트 뒤 보호 서버를 다시 실행해야 합니다.

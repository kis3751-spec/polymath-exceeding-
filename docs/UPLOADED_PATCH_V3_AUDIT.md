## A. 실근이 없는데 ‘근 1개·완전 인증·100%’

```text
(x-1)^4 + 1e-20 = 0
```

범위 `[0.9, 1.1]`. 짝수 거듭제곱은 0 이상이고 입력한 `1e-20`은 Float64로 읽어도 양수이므로 **실근은 없습니다**.

후보의 실제 자동 솔버 반환:

```json
{
  "solutions": [[1]],
  "complete": true,
  "uniqueRootCount": 1,
  "rootIntervals": [{ "lo": 0.9, "hi": 1.1 }],
  "allRootsRepresented": true,
  "grade": "certified",
  "allRootsFoundProbability": 1
}
```

`(x-1)^6+1e-20`도 같은 잘못된 완료를 반환합니다. 반대로 `-1e-20`인 4차·6차 식은 **서로 다른 실근이 2개**인데, 후보는 근 1개로 완료합니다. 4차의 두 근은 대략 `1±1e-5`이고 6차는 대략 `1±4.6415888e-4`입니다.

원인은 `polynomialCoefficients`에서 Float64 계수를 만드는 동안 작은 항이 사라지고, 그 반올림된 다항식을 `evaluatePolynomialCenteredIntervalJet`와 square-free 인증의 원본처럼 사용하기 때문입니다. **반올림한 계수를 정확히 계산하는 것**과 **원래 AST를 정확히 계산하는 것**은 다릅니다.

좌표 평행이동 검사도 이를 드러냅니다.

| 수학적으로 같은 종류의 무근 문제 | 후보 결과        |
| -------------------------------- | ---------------- |
| `x^4+1e-20`, `[-0.1,0.1]`        | 근 0개, 완료     |
| `(x-1)^4+1e-20`, `[0.9,1.1]`     | **근 1개, 완료** |

같은 두 양의 섭동 식을 현재 앱 엔진에도 직접 대입했습니다. 현재 엔진은 4차·6차 모두 `solutions=[]`, `complete=true`, `uniqueRootCount=0`을 반환했습니다. 후보를 적용할 때 재발하는 오류임을 구분합니다.

수정 방향: 보통 정밀도의 다항식 계수는 후보 탐색에만 사용하고, 마지막 인증은 원래 AST에서 해야 합니다. 변환 다항식으로 인증하려면 **계수 생성 과정부터** 정확한 유리수/정수 연산 또는 포함 구간을 보존하고, 원본과 영점이 동치임을 확인해야 합니다. 뒤늦은 exact Taylor만으로 이미 잃은 항을 복구할 수 없습니다.

## B. Gaussian ‘엄밀 상하한’이 정답을 포함하지 않음

`F(x)=x`, `[-1,1]`, 상수 오프셋 `ε~N(0,1)`이면 근은 `x=-ε`입니다. 구간 안 근 개수가 유지될 확률은 정확하게 `P(|ε|≤1)=erf(1/√2)`입니다.

- 100자리 기준: `0.6826894921370858971704650912640758…`
- 후보가 ‘엄밀 구간’으로 반환한 값: **`[0.6826894723352724, 0.6826894723352727]`**

정답은 이 구간 밖입니다. 반경 `0.125, 0.5, 1, 2, 4`에서 실패했고 반경 8은 이 대조를 통과했습니다.

원인은 `erf`의 근사식 자체 오차를 포함하지 않은 채 마지막 합에만 `nextUp/nextDown`을 적용한 것입니다. 최종 Float64 반올림 오차보다 함수 근사 오차가 큽니다. 실용적인 점 추정치일 수는 있지만 ‘엄밀한 상하한’으로 표시할 수 없습니다.

수정 방향: 오차가 증명된 CDF 구간 알고리즘을 쓰거나, 검증된 오차를 포함하는 상하한을 계산해야 합니다. 그 전에는 점 추정이라는 표시와 정확도 범위를 사용하고, 임의 EPS나 마지막 1 ULP 패딩으로 인증하지 않아야 합니다.

## C. `log` 밑 불일치로 확률이 83.18% → 88.60%

점 계산·구간 자동미분의 `log(x)`는 상용로그입니다. 그런데 새 `differentiateNode`는 `ln`과 `log` 모두 `1/x`를 생성합니다. `x=2`에서 올바른 도함수는 약 `0.2171472409516259`인데 후보의 기호 미분 결과는 약 `0.5`입니다.

실제 영향도 확인했습니다. `F(x)=log(x)-x`, 범위 `[0.1,2]`, `σ=1`에서 원래 함수의 극댓값 위치는 `c=1/ln(10)≈0.43429448`입니다. 현재 식에는 실근이 없습니다. 오프셋 아래에도 근이 없는 확률은

```text
Φ(c-log10(c)) + 1 - Φ(2-log10(2))
= 0.831794634553182379…
```

후보는 **`0.8860071247590544`**, 상하한 약 `[0.8860071247590537, 0.886007124759055]`를 반환합니다. 약 **5.42%p 차이**이며 `criticalPointsCertified=true`도 붙입니다.

수정 방향: 기호 미분과 점 평가·구간 AD가 같은 함수 정의를 사용해야 합니다. 파서에서 밑을 바꾸는 방식으로 기존 사용자 모델의 의미를 바꾸지 않습니다.

## D. 중인수 제거 후 원래 임계점을 누락

`F(x)=x^4`, `[-1,1]`, `σ=1`에서 후보는 다음을 반환합니다.

```text
criticalPointsCertified = true
양방향 안전 반경 = [1,1]
P(|ε| < 안전 반경) ≈ 68.27%
```

그러나 원점이 중근이므로 임의의 0이 아닌 작은 오프셋에도 실근 개수는 1개에서 0개 또는 2개로 바뀝니다. **근 개수를 유지하는 양방향 안전 반경은 0**입니다.

후보가 distinct-root 인증을 위해 `x^4→x`로 줄인 뒤, 확률 계산에도 줄인 식의 도함수 `1`을 사용해서 원래 `F′(0)=0`을 놓쳤습니다. 이 사례에서 별도 `domainRootCountInvariance=0` 필드는 맞게 나왔지만, 안전 반경·확률 필드와 모순됩니다.

수정 방향: 중인수 제거식은 허용된 영점 개수 작업에만 쓰고, 섭동·민감도·극값·분기 여유도는 **원래 F와 F′**에서 계산해야 합니다.

## E. 결과 목록 대조 전의 100%와 배포 호환성

`certifyScalarRoots`를 직접 호출하면 아직 `allRootsRepresented`가 `undefined`인데도 `allRootsFoundProbability=1`입니다. 코드의 `!==false`가 ‘미확인’ 상태를 승인합니다. 이 필드의 주석대로 목록 대조까지 완료를 뜻한다면 **`===true`**가 필요합니다. 구간 분리 완료와 화면 결과 목록의 완전성은 구분해야 합니다.

현재 프로젝트에 통째로 대입한 TypeScript 검사에서는 다음도 실패했습니다.

- 수동 시뮬레이션이 사용하는 `manualEquationSource` export 누락. 실제 수동 추적 4개 회귀에서도 런타임 오류가 발생했습니다.
- 기존 근 분류 API `classifyScalarRoot` 및 리포트의 `RootCertificate.reduction` 누락.
- `TangencyVerification` 필드 및 차수/기울기 인수 인터페이스 불일치.
- `CompletenessMetrics.grade`의 정의에 없는 `'partial'` 할당.

이는 수학 반례를 해결해도 별도로 필요한 통합 수정입니다. 2~8차 분류와 퇴화 분기 보호를 예전 버전으로 되돌려서는 안 됩니다.

## 실제 반영한 부분

`src/engine/interval-arithmetic.ts`에서 다음만 분리 적용했습니다.

1. 곱셈 결과를 수학적으로 이미 아는 부호 범위와 교차시킵니다. 양의 언더플로는 `[0, MIN_VALUE]`, 음의 언더플로는 `[-MIN_VALUE,0]`를 보존하며 0과 MIN_VALUE 사이의 실수를 제외하지 않습니다.
2. 역수 구간의 부호도 같은 원칙으로 보존합니다.
3. 정수 거듭제곱에서 정확한 끝점 0·1을 그대로 사용합니다.

이는 범위가 명확한 부호 성질과 독립 정수 유리수 검사로 검증했습니다. 새 영구 회귀는 1,500개 점 산술, 250개 구간의 정확한 모서리 값 포함성, 부호별 언더플로를 검사합니다. 후보의 exact Taylor·square-free 인증 교체, Gaussian 지표, 전체 parser/solver/branches 교체는 적용하지 않았습니다. 새 확률 수치를 사이트 리포트에 표시하지 않습니다.

반영 후 실제 앱 검증: **495개 단위 검사 통과**, **배포 빌드 통과**, **관련 브라우저 시나리오 6개 통과**. 핵심 코드 Markdown도 재생성하고 일치를 확인합니다. 기존 JS 청크 크기 안내는 남아 있습니다.

## 재현하기

기존 11개 게이트는 `scripts/audit-uploaded-patches.mjs`와 첨부에서 추출한 `automatic.ts`, `interval-certification.ts`로 `--underflow`를 사용합니다. 확장 검증은 다음 한 명령으로 임시 프로젝트를 만듭니다.

```bash
node scripts/audit-third-bundle.mjs '/path/확률검증3차.md'
```

프로젝트의 npm 의존성이 설치되어 있어야 하며, 독립 고정밀 기준 생성에는 Python과 **mpmath**가 필요합니다. 도구는 패키지를 자동 설치하지 않습니다. 후보 10개 파일을 덮는 대상은 임시 복사본뿐이며, 현재 회귀 검사·추가 검사·TypeScript 호환성을 실행하고 `audit-summary.json`을 남깁니다. 검사 개수는 실행 시점의 프로젝트 검사 수에 따라 달라질 수 있습니다. 이 후보에는 종료 코드가 0이 아닌 것이 예상됩니다.

- 추가 검사 원문: `scripts/audit-fixtures/v3-expanded.fixture`
- 독립 100자리 기준: `scripts/audit-fixtures/high_precision_reference.py`

다음 후보는 특히 A~D 반례를 먼저 해결해야 합니다. 기존 11개 예제의 통과만을 전체 알고리즘의 인증으로 간주하지 않습니다.
